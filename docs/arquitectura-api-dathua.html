    Recorrido de una petición

    Ejemplo: el dueño mueve un equipo bajo otro padre con PUT /api/nodes/:nodeId. Cada paso puede cortar la petición; el código que regresa está en rojo.

    1Entra a Expressapp.js

    CORS abierto y lectura del JSON.

    400 JSON mal formado
    2Elige la rutaroutes/nodeRoutes.js

    El router fija el orden de middleware. Las rutas /bulk van antes que /:id.

    404 de Express (HTML)
    3Verifica el tokenverifyToken

    Lee el Bearer y deja req.user = { userId, orgId, email }.

    401 sin token · 403 inválido
    4Revisa la suscripciónverifyToken

    Si la prueba venció la marca expired y corta.

    402 TRIAL_EXPIRED
    5Valida los datosupdateNode

    Tipo de equipo, IP y MAC. Validación a mano, sin librería de esquemas.

    400 + mensaje
    6Comprueba el dueñoJOIN sites … orgId = ?

    El equipo debe ser de una sucursal de su organización.

    404 sin acceso
    7Reglas del negociocadena de padres

    Sin ciclos; zona y padre de la misma sucursal.

    400 formaría un ciclo
    8Responderes.json({ message })

    Mensajes en español. Algunos errores llevan code.

    500 + error.message

    1Límite por llavetelemetryLimiter

    10 reportes por minuto por Site API Key.

    429
    2Verifica la llaveverifySiteApiKey

    Header x-site-key. Deja req.site con siteId y orgId.

    401 sin header · 403 inválida

    Las dos credenciales

    Cada endpoint acepta una de dos credenciales. Elegir la correcta es la decisión de seguridad más importante de un endpoint nuevo, porque de ella sale el filtro de organización.

    Authorization: Bearer <JWT>Personas en el dashboard

    Lo firma el login o el registro con JWT_SECRET, dura 24 horas y lleva userId, orgId y email.

    • Toda consulta usa req.user.orgId, nunca un orgId del cuerpo
    • Revisa la suscripción en cada petición
    x-site-key: dth_site_…El agente de una sucursal

    Una llave por sucursal, generada al crearla. Identifica a la sucursal, no a una persona.

    • Solo tres rutas: lista de equipos, telemetría y candidatos
    • La sucursal sale de la llave, nunca del payload
    socket.handshake.auth.tokenTiempo real

    El mismo JWT, enviado al abrir el socket. Sin token no hay conexión.

    • Entra solo a la sala de su usuario
    • join:site revisa que la sucursal sea suya

    Nunca uses io.emit(): manda datos a todas las organizaciones conectadas.

    Lo pendiente, en el orden sugerido. Los dos primeros afectan la confianza del cliente en las alertas; el resto amplía el producto.

    Cómo agregar un endpoint

    Ejemplo real de la lista de pendientes: avisar en tiempo real cuando alguien resuelve un incidente.

    1. Emisor en config/socket.js: una función emit* que siempre usa io.to(sala).
    2. Controlador en controllers/incidentController.js. Filtra por req.user.orgId en la misma consulta que modifica.
    3. Ruta en routes/incidentRoutes.js. Si es una ruta fija como /bulk, regístrala antes de /:id.
    4. Montar el router en app.js solo si es un módulo nuevo.
    5. Frontend: la función en services/api.js y el listener en la vista o el store.
    6. Prueba real: cuenta desechable, HTTP contra la API corriendo y Playwright en el navegador. Prueba también con un token de otra organización.
    7. Limpia los datos de prueba de MySQL y Mongo y anota el cambio en CLAUDE.md.
    config/socket.js
    export const emitIncidentResolved = (siteId, incidentId) => {
  if (!io) return;
  io.to(`site_${siteId}`).emit('incident:resolved', { incidentId });
};
    controllers/incidentController.js
    // PATCH /api/incidents/:id/resolve
export const resolveIncident = async (req, res) => {
  const { orgId } = req.user;
  const [rows] = await pool.query(
    `SELECT i.siteId FROM incidents i
     JOIN sites s ON s.siteId = i.siteId
     WHERE i.incidentId = ? AND s.orgId = ? AND i.isResolved = FALSE`,
    [req.params.id, orgId]);
  if (!rows.length) return res.status(404)
    .json({ message: 'Incidente no encontrado, sin acceso, o ya estaba resuelto' });
  await pool.query('UPDATE incidents SET isResolved = TRUE, resolvedAt = NOW() WHERE incidentId = ?',
    [req.params.id]);
  emitIncidentResolved(rows[0].siteId, Number(req.params.id));
  res.json({ message: 'Incidente resuelto' });
};

    Reglas que no se rompen

    Cada una salió de un error real que ya pasó en este proyecto.

    Filtra por organización en la misma consulta

    Un JOIN con sites y orgId = ?. Ya hubo fugas entre organizaciones en controladores y en sockets.

    No confíes en ids del payload

    Un node_id, siteId o nodeId que manda el cliente se verifica contra su dueño antes de usarlo.

    Nada de io.emit()

    Solo io.to('site_…') o io.to('user_…').

    Rutas fijas antes que /:id

    Si no, Express interpreta bulk o stats como un id.

    Límites con FOR UPDATE

    Contar y crear en la misma transacción con la fila de la organización bloqueada.

    Sin jerga en la interfaz

    Nada de SNMP, EWMA, jitter o score para el dueño. Los textos van en español simple.

    No cifrar SNMP ni integrar pagos sin pedirlo

    Son decisiones pospuestas a propósito por el líder del proyecto.

    Prueba con datos reales y limpia

    HTTP y Playwright contra el sistema corriendo. Después, borra lo de prueba en MySQL y Mongo.

    Códigos de error y límites

    Todas las respuestas llevan message en español. Solo algunos casos agregan un code que el frontend reconoce.

    HTTPcodeCuándo

    401—Sin token, sin header x-site-key, credenciales de login inválidas, contraseña actual incorrecta
    402TRIAL_EXPIREDPrimera petición después de que venció la prueba

    403SITE_LIMIT_REACHEDCrear una sucursal por encima del plan
    403—Token inválido o vencido, Site API Key inválida, límite de zonas, telemetría sin ningún equipo propio
